## 1. 士気の書込経路の監査（全件）

`FleetMorale.morale` を動かせる経路を残らず洗い出しました。

### 外から書く経路（3つだけ）

| 経路 | 量 | 対象 | 向き |
|---|---|---|---|
| `BattleEventManager.AdjustPlayerMorale` | **義勇兵 +8 / 補給線 −5 か +7 / 英雄的奮戦 +6** | **プレイヤー勢力の生存旗艦すべて**（一律・距離無関係） | 上下 |
| `MoraleShock.Propagate` → `ApplyMoraleDelta` | `MoraleShockRules` の基準×距離減衰 | 半径 **16** 以内の旗艦 | 上下 |
| `FleetStrength.TakeDamage` → `OnTakeDamage` | `damage × 0.05`（1発あたり `maxMorale × 0.08` で頭打ち） | 自分 | **下のみ** |

`MoraleShock` の内訳（`MoraleShockRules`）：

| 事象 | 基準 | 味方 | 敵 |
|---|---|---|---|
| 旗艦撃墜 | 18 | −18×減衰（パニック） | **+18×0.5×減衰＝最大 +9**（高揚） |
| 敗走 | 10 | −10×減衰 | 0 |
| 捨てがまり成功 | 12 | **+12×減衰** | 0 |

減衰＝`1 − 距離/16`（半径外は 0）。

### 自分で書く経路（`FleetMorale` 内）

| 箇所 | 量 | 向き | 条件 |
|---|---|---|---|
| `InitializeMorale` | `morale = maxMorale` | 初期化 | 提督データ解決時 |
| `UpdateMorale` 敗走中の立ち直り | `recoveryRate × deltaTime` | **上** | 非交戦かつ**最終交戦から `routedRecoveryDelay`(4秒)** |
| `UpdateMorale` 非交戦の回復 | `recoveryRate × deltaTime` | **上** | 敗走していない＋非交戦（**待ち時間なし**） |
| `UpdateMorale` 交戦低下 | `combatDrainRate × deltaTime` | 下（`maxMorale×0.2` で止まる） | 交戦中 |
| `ApplyIntimidation` | 武名による押し下げ | **下のみ** | 近傍に高武名の敵将 |
| 不退転の下限 | `morale = 1`（`LockedFloor`） | 上（下限保証） | 不退転中 |

**上げられるのは：自然回復／会戦イベント／撃墜高揚／捨てがまり高揚／不退転の下限(=1)、の5つだけ**です。
`ApplyIntimidation` は `Mathf.Max(floor, …)` で押し下げるだけなので**上昇源ではありません**（作業票の「イベントだけと決めつけない」への回答）。

### ★`recoveryRate` は実機で **0.5**（クラス既定 0.7 ではない）

```
$ bash Tools/serialized-value-check.sh FleetMorale recoveryRate
  スクリプト既定 : public float recoveryRate = 0.7f;
  直列化された値 : Assets/Prefabs/FleetUnit.prefab:  recoveryRate: 0.5
  ⚠ 直列化されています（#2548）
```

実機の計算には **0.5** を使わなければなりません。以下の見積りはすべて 0.5 で行います。

## 2. 証跡から**確定できる**こと

### 事実①：t=278.41 の +6.0 は自然回復では説明できない

```
t=270.55  ★敗走 開始（士気 1.0→0.0）
t=278.41  敗走 解除（士気 0.0→6.0）
```

- 敗走中の立ち直りは**最終交戦から4秒**経つまで始まりません（前 task revision7 で被弾も交戦に数えるよう直済み）。
- 経過は 7.86 秒。回復が走りうるのは最大 `7.86 − 4.00 = 3.86` 秒。
- 上限は `0.5 × 3.86 = **1.93**`。クラス既定 0.7 で計算しても 2.70。
- **観測は 6.0。届きません。**

### 事実②：それは**1フレームの跳ね**である

記録側（`FormationChangeRecorder`）は **`Update` で毎フレーム**前回値と比較し、
毎フレーム前回値を更新しています。つまり `0.0→6.0` は**連続する2フレーム間**の変化です。
自然回復の1フレームぶんは `0.5 × deltaTime ≒ 0.0025`。
**3桁違う不連続な跳ね**＝離散的な加算が1回入ったことを示します。

### 事実③：t=280.34 の +4.4 は**敵旗艦の消滅と同一フレーム**

```
t=280.34  敗走 解除（士気 0.0→4.4）
t=280.34  ●消滅（レジストリから除外） QA敵1
```

自軍2 から見て 敵1 は敵です。`MoraleShock` で**敵が受け取れる正の値は旗艦撃墜の高揚だけ**
（敗走・捨てがまり成功はいずれも味方限定）。
`9 × (1 − d/16) = 4.4` → 距離 **約 8.2**（半径 16 の内側）で整合します。

### 事実④：この記録では**原因の通知が構造的に写らない**

`FormationChangeRecorder.AppendNewNotifications` は
**陣形／保持／要請** を含む通知しか出力せず、しかも**読み飛ばした通知の seq も進めて**いました。
「会戦イベント：味方の士気が上がった（+6）」はどの語も含まないため、
**発生していても1行も残りません**。

過去ログに 与ダメ内訳 や 特殊指揮 が写っていたのは、
文面に「**陣形**」が、艦隊名に「（**要請**のみ）」がたまたま含まれていたからで、意図した通過ではありません。

➡ **「イベントの通知が無い」ことは「イベントが起きなかった」証明になりません。**
これが「原因記録がない」の正体です。

## 4. 追加した観測（オプトイン・状態を変えない）

### `MoraleAuditLog`（Core・純ロジック・test-first）

**書き込んだ側が原因を名乗る**台帳です。こちらで推し量りません。

記録するもの：**ゲーム時刻／原因／内訳（イベントID・事象名）／艦隊／前後の士気／前後の敗走／最終交戦からの秒／不退転**。

原因の種別（`MoraleChangeSource`）：
`初期化` `自然回復` `交戦低下` `被弾` `威圧` `不退転下限` `戦況イベント` `撃墜高揚` `敗走衝撃` `捨てがまり高揚` `その他`

ログ洪水を避ける約束：

- **既定は無効**（`Enabled = false`）＝通常プレイでは1件も積みません。
- 有効でも**しきい値未満の増減は積みません**（既定 0.01＝自然回復の毎フレームの刻み 0.0025 は落ちる）。
- ただし**敗走の境界をまたぐ変化は大きさに関係なく必ず残します**＝
  「何が敗走を解いたか」を取りこぼしません（自然回復の 0.0025 で解けた場合もその1件は残る）。
- 容量は**有界**（400件の環状バッファ）、あふれた件数を明示（黙って切り詰めない）。

EditMode **19件**で担保（既定無効・しきい値の境界と絶対値・敗走境界の例外・null安全・有界と打ち切り件数・逆引き・原因別集計・`Clear` がしきい値を変えないこと）。

### 製品側の配線（**観測のみ・挙動は不変**）

| ファイル | 変更 |
|---|---|
| `FleetMorale.cs` | `ApplyMoraleDelta(delta, source, detail)` の**オーバーロード追加**（既存の1引数版はそのまま委譲）。内部の自然回復／交戦低下／被弾／威圧／不退転下限／初期化に原因の札を付けて台帳へ1行。**増減の計算式は一切変えていません** |
| `BattleEventManager.cs` | `AdjustPlayerMorale(delta, eventId)` に。4つの選択肢へ `battle_volunteers` / `battle_supply` / `battle_heroics` を渡すだけ |
| `MoraleShock.cs` | 波及時に事象名（旗艦撃墜／敗走／捨てがまり成功）と、符号から高揚か衝撃かを添える |

いずれも `MoraleAuditLog.Record` は**無効なら即 return** します。通常プレイでの追加負荷は前後値の読み取りだけです。

### 既存の記録の穴を塞いだ（事実④）

`FormationObservationQaMenu` の通知フィルタに
**会戦イベント／撃墜／撃沈／捨てがまり**を追加。原因になりうる稀な通知だけを通します。
これで**次回からは既存の記録にも原因の通知が残ります**。

## 5. Unity での操作手順（ChatGPT 向け）

### メニュー（新設）

| メニュー | 用途 |
|---|---|
| `Ginei/QA: 士気の原因 記録を開始（Play中）` | 記録開始。**既定のしきい値**（自然回復の刻みは省く／敗走の境界は必ず残す） |
| `Ginei/QA: 士気の原因 記録を開始（細かく＝自然回復の刻みも残す）` | しきい値 0。自然回復の量を1フレーム単位で見たいとき |
| `Ginei/QA: 士気の原因 記録を停止` | 停止（記録は残る） |
| `Ginei/QA: 士気の原因 記録を出力` | Console へ出力。末尾に**原因ごとの件数**と**最後に敗走を解いた変化**を添える |
| `Ginei/QA: 士気の原因 記録を消去` | 消去 |

Play を抜けると**自動で無効**になります（通常プレイへ持ち越しません）。

### 手順

1. QA会戦を Play で開始する
2. **`士気の原因 記録を開始（Play中）`**（従来の `陣形保持 変化の記録を開始` も併用してよい）
3. 前回と同じところまで進める＝**不退転が切れたあとの敗走**と、**敵旗艦が落ちる場面**を通す
4. 敗走の解除が観測できたら **`士気の原因 記録を出力`**
5. 出力の **［最後に敗走を解いた変化］** を見る

読み方（**その会戦で起きたこと**についての読み方です）：

| 出力 | 意味 |
|---|---|
| `原因＝戦況イベント（battle_heroics）` | **その場面では**英雄的奮戦 +6 が敗走を解いた |
| `原因＝撃墜高揚（旗艦撃墜）` | **その場面では**敵旗艦の撃墜による高揚が敗走を解いた |
| `原因＝自然回復` ＋ `最終交戦から 4.00 秒以上` | 現行仕様どおりの立ち直り |
| `原因＝自然回復` ＋ `最終交戦から 4 秒未満` | **製品の不具合**（門が効いていない）＝報告してください |
| `原因＝不退転下限` | 不退転が乗った（敗走が解けたのではなく踏みとどまった） |

`記録が無い`ときは開始前・しきい値未満・容量あふれのいずれかです（**記録が無いことは「起きなかった」証明になりません**）。

### ★旧ログ（t=278.41 / 280.34）は、これでは確定しません

この観測が原因を確定させるのは、**記録を開始したあとに新しく起きた事例**だけです。
新しい会戦の記録から、**過去の会戦で起きたことを遡って決めることはできません**
（別の会戦・別の配置・別の抽選であり、同じ原因だった保証がない）。

したがって §3 の2件は、新しい記録が何を示しても**仮説のままです**。
新しい会戦で同じ形（不退転が切れた直後の敗走が +6 前後で解ける／敵旗艦の消滅と同時に解ける）が
**再現できた**なら、その**再現例の原因は確定**します。
旧ログについては「同じ機構で説明できる事例が実在する」という**傍証が増える**にとどまります。
報告の際は<b>再現例の確定した原因</b>と<b>旧ログの仮説</b>を分けて書いてください。

## 7. 付随して分かったこと（仕様変更はしません）

**敗走していない間の自然回復には待ち時間がありません。**

```csharp
if (IsRouted) { if (CanRecover(...4秒...)) 回復; return; }
if (inCombat) { 交戦低下 } else { 回復 }   // ← 待ち時間なし
```

`inCombat` は `FleetWeapon.IsInCombat` ＝「自分が撃った」か「自分の射界に敵がいる」だけなので、
**射界の外から一方的に撃たれている非敗走の艦隊は、被弾で減らしながら同じフレームで自然回復もします**。
4秒の門が効くのは**敗走中だけ**です。

実機の `t=278.41 → 278.55` で士気が 6.0 → 2.1 と落ちたのは、この状態で被弾が回復を上回ったためと整合します。

**これは現行仕様であり、今回は変更しません**（作業票の「製品の回復仕様は変更しない」に従います）。
変えるべきかの判断が要る場合は別 task_id でお願いします。

## 10. revision 3 — Unity 実行での2件失敗を修正

`MoraleSourcePlayModeTests` を Unity で実行し **6件中4合格2失敗**（証跡 `morale-source-r2-all-20260912.xml`）。
レビュー（`morale-source-r2-chatgpt-review-20260912.md`）の指摘は**2件とも当たっていました**。

### 失敗①：`Idle_OnlyNaturalRecovery_AndRateMatches`（自然回復の件数 Expected>1 / Actual 1）

**原因**：`MoraleAuditLog.Clear()` が**しきい値 `MinAbsDelta` を既定 0.01 へ戻して**いました。
試験は `SetUp` で 0（＝刻みまで残す）にしていますが、
観測開始のために途中で `Clear()` を呼んだ時点で 0.01 へ戻ります。
8倍速・高フレームレートでは自然回復の1フレームぶんが
`0.5 × (0.0023 × 8) ≒ 0.009` と**しきい値をわずかに下回る**ため、ほとんどが黙って落ちていました。

**修正**：`Clear()` は**記録を消すだけ**にしました（`Enabled` も `MinAbsDelta` も変えない）。
しきい値を戻すのは新設の `ResetSettings()` を明示的に呼んだときだけです。
「途中で区切る」のが主な使い方なのに、区切った拍子に設定が失われるのは落とし穴でした。
試験側にも「区切ったあともしきい値が 0 のままであること」の assert を足し、
EditMode に `Clear_DoesNotTouchTheThreshold` / `ResetSettings_RestoresThresholdOnly` を追加しています。

### 失敗②：`RoutedUnderFire_NoNaturalRecoveryAtAll`（被弾の件数 Expected>1 / Actual 0）

**原因**：**assert の選び方の誤り**です。
敗走後の士気は 0 で、そこへ被弾しても下限 0 でクランプされ**士気が動きません**。
台帳は「**変化**」を残す仕組みなので、被弾が届いていても記録は 0 件になります。
＝「継続被弾の証明」に台帳の件数を使ったのが不適切でした（製品側は正常）。

**修正**：継続被弾は**兵力が実際に減ったこと**（`strength.strength` の減少）と**撃った回数**で示します。
あわせて「敗走中の士気が下限 0 に張り付いていること」も assert し、
**なぜ台帳が動かないのか**を試験自身が説明するようにしました。

肝心の `自然回復 0 件` はそのまま維持しています。これは空振りになりません：
立ち直りの回復が1度でも走れば士気は 0 から正へ動き、**敗走の境界を跨ぐ**ため
**しきい値に関係なく必ず記録される**からです（`Enabled` が真であることも assert）。
